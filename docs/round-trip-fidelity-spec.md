# Round-Trip Fidelity Specification

**Constitutional reference**: §G.8, §DW13.1–§DW13.4  
**Constitution version**: v1.21.0  
**Introduced**: 2026-04-04 (Round 8 — Q8)  
**Status**: Normative

## 1. Purpose

This document provides the normative technical specification for preference
round-trip fidelity as defined in §G.8 and §DW13.1–§DW13.4. It covers:

- Canonical field definitions: included and excluded fields (§2)
- Why full-record equality is not achievable and must not be required (§3)
- Reference Python constants for shared comparison logic (§4)
- CI test specification (§5)
- Migration patch for existing exporters/importers and tests (§6)
- Round-trip process diagram (§7)

---

## 2. Canonical Field Definitions (§DW13.1 / §DW13.2)

### 2.1 Fields Included in Fidelity Comparison (§DW13.1)

The following fields MUST match exactly after an export–import cycle. These
are the **semantic preference fields** that define user intent.

| Field                 | Description                                   |
|-----------------------|-----------------------------------------------|
| `preference_category` | The category grouping this preference belongs to |
| `preference_key`      | The unique key identifying the preference within its category |
| `preference_value`    | The actual preference value (may be of any supported type) |
| `value_type`          | The declared type of the preference value (string, int, bool, list, object, etc.) |

All four fields MUST be present in the export artifact for every preference.
An importer that receives a record with any of these fields absent MUST treat
it as a malformed record and skip it with a user-visible skipped-item entry
(§VI.1).

### 2.2 Fields Excluded from Fidelity Comparison (§DW13.2)

The following fields MUST be excluded from round-trip fidelity comparison.
Including them in the comparison makes round-trip fidelity impossible and
non-portable across implementations.

| Field                | Reason for Exclusion                                    |
|----------------------|---------------------------------------------------------|
| `created_at`         | Set to original creation time; unchanged by import; will always differ |
| `modified_at`        | Updated to import timestamp; will always differ         |
| `imported_at`        | Import-time stamp; does not exist before first import   |
| `record_id`          | Internal storage identifier; regenerated by each implementation |
| `version`            | Storage record schema version; implementation-specific  |
| `migration_flags`    | Implementation-internal migration state; not user-facing |
| Any other metadata   | Any field not in §2.1 is excluded by default            |

### 2.3 Semantic vs. Record Identity

| Comparison type     | Required? | Notes |
|---------------------|-----------|-------|
| Semantic field match | YES (§DW13.1) | Category, key, value, value_type |
| Timestamp match     | NO (§DW13.2) | Never required |
| Record ID match     | NO (§DW13.2) | Never required |
| JSON byte-for-byte  | NO (§DW13.4) | Ordering and formatting differences are permitted |
| Field ordering match| NO (§DW13.4) | Record order and JSON field order are not fidelity signals |

## 3. Why Full-Record Equality is Not Achievable (§DW13.4)

Full-record byte-for-byte identity after an export–import cycle is impossible
for the following structural reasons:

| Source of difference | Example |
|----------------------|---------|
| `created_at` preserved from original | 2025-01-15T10:00:00Z (original) ≠ 2026-04-04T12:00:00Z (import) |
| `modified_at` reflects import time | Set by importer |
| `record_id` is regenerated | UUID or integer assigned by target DB |
| Record ordering differs | INSERT ORDER may differ |
| JSON field ordering differs | `{"value": 1, "key": "x"}` vs `{"key": "x", "value": 1}` |
| Whitespace / serialization | Pretty-printed vs compact JSON |

These differences are not defects. They are expected behavior of a portable,
database-backed preference system.

## 4. Reference Constants (Python)

This module MUST be imported by all preference export/import code and all
round-trip fidelity tests. Using the shared constants prevents drift between
implementation and tests.

```python
# src/utilities/preferences/round_trip_fields.py
#
# Canonical field definitions for round-trip fidelity.
# Constitutional reference: §G.8, §DW13.1–§DW13.2

# Fields that MUST match after export → import (§DW13.1)
ROUND_TRIP_FIELDS: tuple[str, ...] = (
    "preference_category",
    "preference_key",
    "preference_value",
    "value_type",
)

# Fields that MUST be excluded from fidelity comparison (§DW13.2)
METADATA_FIELDS: tuple[str, ...] = (
    "created_at",
    "modified_at",
    "imported_at",
    "record_id",
    "version",
    "migration_flags",
)


def semantic_key(record: dict) -> dict:
    """
    Extract only the semantic preference fields from a record.
    Used in round-trip fidelity comparisons.

    Raises KeyError if any ROUND_TRIP_FIELDS are absent.
    """
    return {field: record[field] for field in ROUND_TRIP_FIELDS}


def semantic_set(records: list[dict]) -> set[tuple]:
    """
    Convert a list of preference records to a set of semantic tuples.
    Suitable for set-equality comparison in tests.
    """
    return {
        tuple(record[f] for f in ROUND_TRIP_FIELDS)
        for record in records
    }
```

## 5. CI Test Specification (§DW13.3)

### 5.1 Required Tests

| ID  | Test Scenario                                    | Assertion |
|-----|--------------------------------------------------|-----------|
| T1  | Simple round-trip (diverse types)                | `semantic_set(before) == semantic_set(after)`; no extra or missing keys |
| T2  | Metadata explicitly ignored                      | Test passes even when `created_at`, `modified_at`, `record_id` differ |
| T3  | Ordering and formatting independence             | Shuffle record order + reformat JSON → semantic state still matches |
| T4  | Partial export/import (subset of categories)     | Only exported prefs present after import; each has identical semantic fields |
| T5  | Backward compatibility (legacy export version)   | Same semantic fidelity rules hold for v0 exports |
| T6  | Unknown category on import                       | Import does not crash; unknown category handled according to skip policy |
| T7  | Missing semantic field in export record          | Importer skips record; skipped-item summary entry produced (§VI.1) |
| T8  | Silent value coercion detection                  | If importer changes value or value_type without explicit migration rule → test fails |

### 5.2 Anti-Patterns to Reject

The following test patterns MUST be corrected as soon as found:

| Anti-pattern                                        | Why it's wrong |
|-----------------------------------------------------|----------------|
| `assert record_before == record_after`              | Compares full records including timestamps |
| `assert df_before.equals(df_after)`                 | Same — includes metadata columns |
| `assert json_before == json_after`                  | Byte-for-byte equality including timestamps |
| Comparing only counts: `assert len(before) == len(after)` | Does not verify values |
| Skipping the round-trip test entirely               | §DW13 requires it |

### 5.3 CI Enforcement Rules

| Rule | Description                                                       | Failure |
|------|-------------------------------------------------------------------|---------|
| R1   | At least one explicit round-trip test compares `semantic_set()` before and after | Build fails |
| R2   | No test asserts full-record equality including metadata fields     | Build fails if found |
| R3   | `ROUND_TRIP_FIELDS` constant used in export code and tests        | Build fails if tests define their own field list |
| R4   | Importer does not silently coerce `preference_value` or `value_type` | Build fails if coercion detected without migration rule |
| R5   | T7 (missing semantic field → skip) present and passing            | Build fails if absent |

## 6. Migration Patch for Existing Code

### Step 1 — Add Canonical Constants Module

Create `src/utilities/preferences/round_trip_fields.py` as defined in §4.

### Step 2 — Update Exporters

Ensure all preference exporters emit the four semantic fields for every
preference record:

```python
from round_trip_fields import ROUND_TRIP_FIELDS

def serialize_preference(record: dict) -> dict:
    """Serialize a preference record for export."""
    # Always emit semantic fields
    serialized = {field: record[field] for field in ROUND_TRIP_FIELDS}
    # Optionally attach metadata in a separate 'meta' sub-object
    serialized["meta"] = {
        "created_at": record.get("created_at"),
        "modified_at": record.get("modified_at"),
        "record_id": str(record.get("record_id", "")),
    }
    return serialized
```

### Step 3 — Update Importers

On import, reconstruct preferences using only `ROUND_TRIP_FIELDS`. Treat
metadata as optional and non-authoritative:

```python
from round_trip_fields import ROUND_TRIP_FIELDS, METADATA_FIELDS

def import_preference(record: dict) -> dict:
    """
    Reconstruct a preference from an import record.
    Only ROUND_TRIP_FIELDS are authoritative.
    METADATA_FIELDS are discarded; the database regenerates them.
    """
    missing = [f for f in ROUND_TRIP_FIELDS if f not in record]
    if missing:
        raise ValueError(f"Malformed import record: missing fields {missing}")
    return {field: record[field] for field in ROUND_TRIP_FIELDS}
    # Database layer (created_at, modified_at, record_id) are set on INSERT
```

### Step 4 — Update Tests

Replace any tests that compare full records with compliant tests:

```python
from round_trip_fields import semantic_set

def test_round_trip_fidelity(exporter, importer, preference_store):
    """
    T1: export → import → semantic fields match.
    T2: timestamps and IDs are NOT compared.
    """
    original_records = preference_store.get_all()

    export_data = exporter.export(original_records, passphrase="test-pass")
    importer.import_data(export_data, passphrase="test-pass")
    imported_records = preference_store.get_all()

    # Compare only semantic fields (§DW13.1)
    assert semantic_set(original_records) == semantic_set(imported_records), (
        "Round-trip fidelity failed: semantic fields differ after import"
    )
    # Explicitly confirm timestamps are NOT compared (§DW13.2 compliance)
    # (no assertion on created_at, modified_at, record_id, etc.)


def test_timestamps_differ_after_round_trip(exporter, importer, preference_store):
    """
    T2: demonstrates metadata differs while fidelity still passes.
    """
    original_records = preference_store.get_all()
    export_data = exporter.export(original_records, passphrase="test-pass")
    importer.import_data(export_data, passphrase="test-pass")
    imported_records = preference_store.get_all()

    # Semantic fidelity holds
    assert semantic_set(original_records) == semantic_set(imported_records)

    # Metadata legitimately differs — this is expected behavior, not a bug
    for orig, imported in zip(original_records, imported_records):
        assert orig.get("modified_at") != imported.get("modified_at") or True
        # (True guard: metadata fields MAY differ; test documents but does not require it)
```

### Step 5 — Document in Developer Docs

Add the following note to the developer-facing preference portability section:

> Round-trip fidelity (§G.8, §DW13.1–§DW13.4) is defined over **semantic
> fields only**: `preference_category`, `preference_key`, `preference_value`,
> and `value_type`. System-generated metadata fields (`created_at`,
> `modified_at`, `record_id`, etc.) are regenerated on import and MUST NOT
> be included in fidelity comparisons.

## 7. Round-Trip Process Diagram

```
          EXPORT PHASE
          ------------

+-------------------------------+
| 1. Read current preferences   |
|    (all records)              |
+---------------+---------------+
                |
                v
+-------------------------------+
| 2. Extract semantic fields    |
|    preference_category        |
|    preference_key             |
|    preference_value           |
|    value_type                 |
+---------------+---------------+
                |
                v
+-------------------------------+
| 3. Attach optional metadata   |
|    (created_at, record_id,    |
|     modified_at, etc.)        |
|    → goes into "meta" object  |
+---------------+---------------+
                |
                v
+-------------------------------+
| 4. Encrypt + serialize        |
|    (AES-256-GCM per §VI.4)    |
+-------------------------------+


          IMPORT PHASE
          ------------

+-------------------------------+
| 5. Decrypt envelope (§VI.4)   |
+---------------+---------------+
                |
                v
+-------------------------------+
| 6. Parse records              |
+---------------+---------------+
                |
                v
+-------------------------------+
| 7. Reconstruct preferences    |
|    using ONLY:                |
|    - preference_category      |
|    - preference_key           |
|    - preference_value         |
|    - value_type               |
+---------------+---------------+
                |
                v
+-------------------------------+
| 8. Store preferences          |
|    Database regenerates:      |
|    - created_at               |
|    - modified_at              |
|    - record_id                |
|    - imported_at              |
+---------------+---------------+
                |
                v
+-------------------------------+
| 9. Round-trip fidelity check  |
|    Compare ONLY semantic      |
|    fields (§DW13.1).          |
|    Metadata is NEVER compared |
|    (§DW13.2).                 |
+-------------------------------+
```
